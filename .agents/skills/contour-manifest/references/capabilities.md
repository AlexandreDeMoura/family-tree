Capabilities are concrete, bounded abilities of the product's intended users. Each describes one coherent user task and its observable result at the product level. Identify those users from the PRD or product brief; the developer working on the repository is not automatically a product persona. Developer-facing products can have developer users and real CLI or API surfaces.

Before adding or updating a capability, read the whole capability list and apply these scope rules:
1. State the ability as “A [product persona] can [concrete action] [object] [essential context or limit].” Name the task, not a broad benefit such as “understand the family” or “maintain a family tree.” Use a concise action phrase for `name`; use `why` to explain its purpose and any scope boundary the name cannot express.
2. Identify a starting situation and an observable completion or usable state through a real product surface. Browsing can end in a usable view; it need not mutate data. Would the outcome stay conceptually the same if the technical stack changed? UI concepts that define the experience, such as a canvas, are valid; component names and libraries do not define the capability.
3. Group steps that complete the same task. Group ordinary create, edit, and delete operations on the same user-facing object when they share purpose and access context. Do not split them by button, endpoint, form, or implementation order. Split an operation only when it has a distinct user purpose or materially different access or lifecycle, such as approving or publishing a record.
4. Split an umbrella when it contains separate user tasks with different results. Managing tree containers, editing relatives, exploring the tree, and sharing access are separate abilities even if they share a page or form a larger journey. Keep the list at this task level; do not list both an umbrella and its constituent abilities, or a task and each of its interaction details.
5. Compare with existing entries by meaning, not wording. State which existing ability owns the behavior, or why it needs a new entry. A new screen, persona, rule, or implementation commit alone is not a new ability. Builder-provided scope examples anchor granularity; do not broaden or split them merely to match a work plan. When context leaves a material boundary unresolved, record the question instead of inventing scope.

Family-tree scope examples (illustrative abilities, not claims that they are implemented):
- “Create multiple family trees and select one to browse”: tree containers and selection; relative editing and canvas navigation belong to other abilities.
- “Create a private link for people to view a tree without an account”: link creation and recipient access are steps of the same sharing task; copying the link is a detail.
- “Explore all relatives of a selected family tree on a canvas”: pan, zoom, branch focus, and opening a person card are details of exploration unless the product defines a separate task with its own result. Do not add a capability solely because the card was built separately.
- “Create, edit, and delete a relative in a selected family tree”: one record-management ability; fields and validation messages are details. Do not claim the whole ability shipped if only creation exists.
Connecting relatives or managing their photos can be additional abilities when they are separate user tasks. A memorable-facts field alone belongs to relative editing; combining photos and facts under a broad benefit does not establish one task.

Route setup and technology choices to `project.yaml`; system parts, infrastructure, libraries, validation engines, and persistence to `boundaries.yaml`; user-facing promises and limits to capability-owned `contracts/`; internal guarantees and invariants to part-owned `contracts/`; pages, endpoints, commands, and jobs to `surface.yaml`; and durable reasons to `decisions.yaml`. For example, “Validate and derive a family graph” belongs in a part and its contract; “Connect relatives as parents, children, or partners” is a user capability, with impossible-relationship prevention in its supporting contracts.

Do not create one capability per implementation commit or technical milestone. The same product behavior must produce the same capability boundaries whether delivered in one commit or many. Before editing, map the requested change to existing abilities. Update their code, evidence, contracts, and status as work progresses; add an entry only for a distinct user task. Reuse stable capability IDs when the task stays the same. For a real split or merge, update all affected references and contract ownership together, preserve valid evidence, and explain the scope change. Never silently widen an existing shipped claim to include unfinished behavior.

Capability statuses describe the user outcome:
- `planned`: the outcome has been chosen; no completed implementation is claimed. Empty references and an omitted `last_verified` are honest here.
- `in-progress`: some implementation exists, but the outcome is not yet usable and verified end to end.
- `shipped`: the intended user can complete the outcome through a real product surface, with end-to-end verification evidence. Record its `doors` and genuine `verified_by` paths. Unit tests of a foundation alone do not establish delivery; respect the builder's manual acceptance requirements and never invent evidence.

For greenfield work, seed a small outcome checklist from the PRD's MVP user loop before implementation. Keep unbuilt outcomes planned, and advance the same entries as work progresses. For existing code, distinguish implemented outcomes from documented plans; do not infer a roadmap from folders or commits. Completed foundations can coexist with zero shipped capabilities. A shipped part or contract does not automatically ship its dependent capabilities. Semantic warnings are prompts for review, not proof that an outcome is wrong; confirm the evidence before changing status or ownership.
