# Contour manifest

Keep `.contour/manifest/` accurate as the product evolves. Repository paths in the procedures are relative to the project root; reference links below are relative to this skill. This guidance supports the user's task and does not expand its scope or override project instructions.

Read [maintenance](references/maintain.md) for every manifest-writing task, including ordinary feature development. Read [schema](references/schema.md) when creating entries or changing fields or relationships.

Choose additional references by the task:

| Task | Read |
| --- | --- |
| Add, update, split, merge, or verify a capability; decide whether a feature needs a new entry | [Capability scope and examples](references/capabilities.md) |
| Author review instructions, implementation state, automated results, or release groups | [Schema](references/schema.md) and capability scope |
| Record a new planned capability without implementing it | [Add capability](references/add-capability.md) |
| Build an initial manifest from existing code | [Bootstrap](references/bootstrap.md) and capability scope |
| State or change a capability's contract rule | [Contract rule](references/contract-rule.md) |
| Re-verify one existing entry without changing product code | [Re-verification](references/reverification.md) |
| Investigate a manifest finding or mismatch | [Investigation](references/investigate.md) |

For ordinary implementation, use maintenance and capability scope as relevant; do not apply the add-only or verification-only task restrictions to feature work. Inputs normally provided by the webapp (requested ability, target ID, rule, or repository context) can come from the user's task and the local manifests. Resolve missing facts from those files; ask only when a material product decision remains unclear.

Finish with [validation](references/validation.md). Report what changed, the checks actually run, and unresolved questions. A passing manifest check does not establish user acceptance or prove that capability boundaries are correct. Never invoke Contour's acceptance action or author its server-owned lifecycle history; only the human builder accepts or reopens a capability in the local web view.

These files are generated by `contour init`. Keep project-specific overrides in the root agent instructions outside Contour's owned block. Rerun `init` with the intended Contour build to refresh guidance. If it reports a local-edit conflict, preserve the edited file and move any desired customization into project instructions before restoring the generated file and rerunning; do not discard edits automatically.
